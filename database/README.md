# MineSafe SQL Server Database

This directory contains the Microsoft SQL Server schema, migrations, and seed scripts for the MineSafe Mobile Incident Reporting System. The SQL schema is the authoritative database contract used by the ASP.NET Core API and Android application.

## Database architecture

The central database contains twelve tables created in dependency order by the scripts in `database/schema/`.

Account authorization uses normalized assignment tables:

- `Accounts` stores identity, authentication, activation, and concurrency data. It does not contain `RoleID`.
- `AccountRoles` assigns one or more roles to an account. `IsActive` preserves historical assignments without deleting them.
- `AccountLocations` assigns the locations an account may access and records `IsDefault`, `IsActive`, `AssignedAt`, and `AssignedBy`.
- `Roles` and `Locations` provide the referenced role and location records.

The API is responsible for enforcing endpoint permissions and location-scoped access. SQL Server preserves the assignment data and referential integrity; it does not implement authorization rules.

## Offline report synchronization

`Reports` uses two identifiers for different purposes:

- `ReportID` is the SQL Server identity primary key.
- `ReportNumber` is the unique human-readable report reference.
- `ClientReportId` is a required, unique `UNIQUEIDENTIFIER` generated by the mobile application when a report is created offline.

The API must look up `ClientReportId` during synchronization. If the same mobile report is uploaded again after a timeout or retry, the existing server report can be returned instead of inserting a duplicate. The database unique constraint is the final safeguard against duplicate client identifiers.

New reports must supply `ClientReportId`; the database does not generate it automatically.

## Incident timestamps

The report timestamps have separate meanings:

- `OccurredAt`: when the incident or hazard actually occurred, supplied by the client.
- `CreatedAt`: when the report record was created.
- `SubmittedAt`: when the report was submitted to or accepted by the server; it may be later because the device can be offline.
- `UpdatedAt`: the most recent report update, when applicable.

The offline-fields migration backfills `OccurredAt` for historical reports from `CreatedAt`. This preserves existing rows but is only an approximation because the actual historical incident time was not previously stored.

## Initial database deployment

Run the schema scripts against an empty database in this exact order:

1. `schema/001_Roles.sql`
2. `schema/002_IncidentTypes.sql`
3. `schema/003_ReportStatuses.sql`
4. `schema/004_Locations.sql`
5. `schema/005_Accounts.sql`
6. `schema/006_AccountRoles.sql`
7. `schema/007_AccountLocations.sql`
8. `schema/008_Reports.sql`
9. `schema/009_ReportAttachments.sql`
10. `schema/010_ReportReviews.sql`
11. `schema/011_ReportAuditLog.sql`
12. `schema/012_Notifications.sql`

Each file contains one `CREATE TABLE` statement followed by its related indexes. Do not run the migration after a fresh deployment made from the current schema unless deployment tooling requires migrations to be recorded; the current base schema already includes the offline fields.

Seed scripts in `database/seed/` are separate from schema creation and should be reviewed and executed only after all schema scripts complete successfully.

## Updating an existing database

Apply migration scripts from `database/migrations/` in numeric order. For the offline report fields, execute:

```sql
:r database/migrations/001_AddReportOfflineFields.sql
```

The `:r` directive is supported by SQLCMD mode. Alternatively, open the migration file in SQL Server Management Studio and execute it against the intended database.

`001_AddReportOfflineFields.sql`:

- checks that `dbo.Reports` exists;
- adds missing columns as nullable before backfilling existing rows;
- assigns a distinct `NEWID()` to each historical report;
- uses `CreatedAt` as the documented historical `OccurredAt` approximation;
- changes both columns to `NOT NULL`;
- adds uniqueness for `ClientReportId` when no equivalent unique index exists;
- uses a transaction, `XACT_ABORT`, and `TRY/CATCH` rollback;
- can be executed again safely when the expected columns and uniqueness already exist.

Back up the target database and test migrations in a development environment before production deployment.

## Validation after deployment

Confirm the update with queries such as:

```sql
SELECT
    c.name AS ColumnName,
    TYPE_NAME(c.user_type_id) AS DataType,
    c.is_nullable,
    c.scale
FROM sys.columns AS c
WHERE c.object_id = OBJECT_ID(N'dbo.Reports')
  AND c.name IN (N'ClientReportId', N'OccurredAt');

SELECT ClientReportId, COUNT(*) AS DuplicateCount
FROM dbo.Reports
GROUP BY ClientReportId
HAVING COUNT(*) > 1;

SELECT COUNT(*) AS MissingRequiredValues
FROM dbo.Reports
WHERE ClientReportId IS NULL OR OccurredAt IS NULL;
```

Also verify that `PK_Reports` still covers `ReportID`, `UQ_Reports_ReportNumber` remains present, and a unique constraint or unfiltered unique index covers only `ClientReportId`.

## API integration requirements

The ASP.NET Core API must follow these database contracts:

- `Accounts` does not contain `RoleID`.
- Role assignments must use `AccountRoles`, including its `IsActive` state.
- Location assignments must use `AccountLocations`, including its `IsActive` and `IsDefault` state.
- `Accounts.Email` is mandatory and limited to `NVARCHAR(255)`.
- `Reports.ClientReportId` is required, unique, and supplied by the mobile client.
- `Reports.OccurredAt` is required and represents the actual incident time.
- `Reports.ReportID` remains the primary key and `ReportNumber` remains a separate unique reference.
- The attachment uploader column is named `ReportAttachments.UploadedByAccount`; a differently named C# property must be mapped explicitly to it.
- Entity Framework mappings and API validation must respect every SQL column's length and nullability.
- Accounts and assignments should be deactivated rather than deleted so historical reports and audit records remain valid.

The API developer should not use `EnsureCreated` as a replacement for executing the authoritative SQL schema and ordered migrations against shared environments.
